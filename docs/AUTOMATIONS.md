# Automation Control Plane

## Purpose

Althea Pay automations consume canonical operational events and execute governed side effects. They are part of the Revenue Operating System and are scoped to an organization, not to a single operator.

The canonical operator surface is:

- `/dashboard/automations`

The runtime is:

- `automation-engine-v2`
- `automation-retry-worker`

Event producers that invoke the runtime include:

- `funnel-events`
- `integration-event-processor`

## Tenant model

The following tables carry a required `organization_id`:

- `automation_rules`
- `automation_executions`
- `automation_execution_attempts`

Rules are selected by organization. Execution idempotency is enforced on:

`organization_id + rule_id + execution_key`

This means a rule created by an authorized admin or manager can react to events generated by another user inside the same organization without crossing tenant boundaries.

Direct authenticated table mutations are revoked. The browser can read tenant-scoped state through RLS, but rule changes go through governed RPCs.

## Rule lifecycle

Operator RPCs:

- `automation_rule_upsert_v1`
- `automation_rule_delete_v1`
- `automation_operations_v1`
- `crm_cancel_automation_execution`
- `crm_replay_automation_execution`

Allowed rule statuses:

- `draft`
- `active`
- `paused`

Deleting a rule with execution history does not erase audit history. The rule is paused instead.

## Triggers

The builder uses canonical funnel event types from `funnel_event_types`.

A trigger can filter by:

- canonical `event_type`;
- one funnel or all funnels;
- conditions evaluated against the event context/payload.

The condition evaluator supports bounded nesting and comparison operators. The governed create/update RPC caps the operator builder at 20 conditions.

## Actions

The governed operator contract currently exposes:

- `log`
- `alert`
- `send_crm_message`
- `set_conversation_status`

A rule may contain up to five ordered actions.

`send_crm_message` is currently enabled by the builder only for `funnel_chat`, where conversation context is already under Althea control.

## Financial authority boundary

Generic automations do **not** directly mutate payment or sale state.

The engine rejects legacy generic actions:

- `update_transaction`
- `update_sale`

with `financial_authority_action_forbidden`.

Payment transitions, gateway changes, refunds, reconciliation and other financial mutations remain under their canonical Payment/Gateway/Financial authorities. This prevents an arbitrary automation rule from bypassing payment state machines and audit controls.

## Reliability

The runtime includes:

- stable execution keys;
- organization-scoped idempotency;
- retry queue;
- exponential backoff;
- scheduled execution claiming;
- bounded per-rule rate limiting;
- dead-letter state;
- manual replay;
- manual cancellation;
- per-attempt audit rows.

The retry worker uses organization-scoped rate limits.

## Security

- Anonymous access to automation tables/RPCs is denied.
- Reads use organization RLS.
- Rule mutations require owner/admin/manager.
- Rule deletion requires owner/admin.
- Replay/cancel requires owner/admin/manager.
- Retry/claim/dead-letter/rate-limit worker RPCs remain service-role only.
- Edge Functions preserve their existing custom internal-secret authentication and therefore keep `verify_jwt=false`.
- No internal secret is returned to browser code.

## Observability

`automation_operations_v1` provides bounded operator data:

- rule counts/status;
- executions in the last 24 hours;
- completion/failure counts;
- dead-letter backlog;
- scheduled/pending backlog;
- recent rule execution health;
- recent executions;
- canonical event types;
- tenant funnels.

NOC metrics, queue counts, incidents and Realtime subscriptions use `organization_id` for automation state and drill down to `/dashboard/automations`.

## Rollout compatibility

The organization migration includes compatibility triggers that derive `organization_id` from the rule/profile when older runtime code omits it. The legacy user-scoped rate-limit RPC delegates to the organization-scoped implementation during rollout.

Production Edge Functions were deployed from the same GitHub source after the organization migration, eliminating that temporary compatibility dependency for the updated runtime.
